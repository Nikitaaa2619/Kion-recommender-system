# KION Recommender System

Учебный проект рекомендательной системы для онлайн-кинотеатра на основе открытого обезличенного датасета KION.

Цель — пройти путь от исследования данных и простого baseline до двухэтапной рекомендательной системы и сервисной инфраструктуры.

## Текущий статус

Реализованы:

- загрузка и первичный аудит полного датасета;
- временное разбиение на train, validation и test;
- сохранение подготовленных данных в Parquet;
- рекомендации по популярности;
- fallback по популярности для пользователей без истории;
- Recall@K, MAP@K, NDCG@K и покрытие каталога;
- отдельная оценка пользователей с историей и без неё;
- разреженная матрица взаимодействий;
- обучение и оценка ALS с 32 и 64 факторами;
- item-to-item по косинусному сходству аудиторий;
- объединение кандидатов трёх источников с сохранением позиций;
- оценка полноты объединённого набора и дополнительного вклада ALS;
- журнал экспериментов;
- автоматические тесты и проверка кода Ruff.

Item-to-item с дополнением по популярности показывает лучшее качество top-10 среди проверенных моделей на validation.

Объединение до 100 кандидатов от каждого источника достигает Candidate Recall 0.529598. ALS добавляет попадания, отсутствующие у популярности и item-to-item.

Следующий этап — временная схема подготовки обучающих примеров для ранжирования без утечки будущего.

Ранжировщик, FastAPI, Airflow, MLflow, хранилище рекомендаций и инфраструктура развёртывания пока не реализованы.

## Целевая архитектура

1. Генерация кандидатов: популярность, ALS и item-to-item.
2. Объединение кандидатов и расчёт признаков.
3. Ранжирование: CatBoost или LightGBM.
4. Выдача top-K рекомендаций через сервис.

Модели сравниваются на едином временном разбиении. Для пользователей без истории используется популярность.

## Протокол offline-оценки

- Оцениваются все пользователи с взаимодействиями в validation.
- Релевантными считаются все объекты, просмотренные пользователем в validation.
- Используется бинарная релевантность: длительность и процент просмотра не влияют на метрики.
- Просмотренные в train объекты исключаются из рекомендаций.
- Объекты validation, отсутствующие в train, остаются в целевых просмотрах.
- Пользователи получают одинаковый вес при усреднении метрик.
- Warm — пользователи с историей в train.
- Cold — пользователи без истории в train. Это не обязательно недавно зарегистрированные пользователи.

### Метрики

- **Recall@K** — доля релевантных объектов среди первых K рекомендаций.
- **MAP@K** — среднее AP@K по пользователям. AP суммирует точность на позициях уникальных попаданий и делится на `min(число релевантных объектов, K)`.
- **NDCG@K** — сумма весов уникальных попаданий, нормированная на идеальный список. Вес позиции: `1 / log2(position + 1)`.
- **Coverage@K** — число уникальных объектов во всех списках top-K, делённое на размер каталога train.
- **Candidate Recall** — доля релевантных объектов во всём наборе кандидатов, усреднённая по пользователям. Порядок кандидатов не учитывается.

## ALS

Используется implicit ALS на бинарной матрице взаимодействий.

Для Warm модель исключает просмотренные объекты. Для Cold используется популярность.

Текущая конфигурация обучения:

- factors: 64;
- regularization: 0.1;
- iterations: 15;
- alpha: 20.0;
- random_state: 42;
- num_threads: 4;
- CPU.

```bash
OPENBLAS_NUM_THREADS=1 uv run python -m kion_recs.models.als
```

Оценка текущей конфигурации:

```bash
OPENBLAS_NUM_THREADS=1 uv run python -m kion_recs.evaluate_als
```

Текущие скрипты обучения и оценки ALS используют `artifacts/als_f64`.

```text

├── model.npz
├── train_interactions.npz
├── user_ids.parquet
└── item_ids.parquet
```

Повторное обучение перезаписывает файлы в этой папке.

Первый эксперимент с 32 факторами сохранён локально в `artifacts/als`. Остальные параметры совпадают с конфигурацией выше.

Для повторения первого эксперимента нужно изменить число факторов и согласованно задать папку артефактов в обучении и оценке. Автоматический выбор конфигурации через командную строку пока не реализован.

## Item-to-item

Объекты сравниваются по косинусному сходству их аудиторий в train:

```text
similarity(A, B) = общие зрители / sqrt(зрители A × зрители B)
```

На объект сохраняется до 50 соседей с положительным сходством. Сам объект исключается.

Балл кандидата — сумма сходств с просмотренными объектами.

При оценке готовой выдачи top-10 неполные списки дополняются популярностью. Для Cold используется популярность.

Демонстрация похожих объектов:

```bash
OPENBLAS_NUM_THREADS=1 uv run python -m kion_recs.item_to_item_demo
```

Построение соседей:

```bash
OPENBLAS_NUM_THREADS=1 uv run python -m kion_recs.train_item_to_item
```

Оценка:

```bash
OPENBLAS_NUM_THREADS=1 uv run python -m kion_recs.evaluate_item_to_item
```

Артефакты:

```text
artifacts/item_to_item_k50/
├── neighbors.npz
├── train_interactions.npz
├── user_ids.parquet
└── item_ids.parquet
```

Повторное построение перезаписывает файлы в этой папке.

Сходство вычисляется пакетами по 128 объектов. После отбора top-50 матрица соседей может быть несимметричной.

Для текущего train:

- объектов: 15 415;
- связей: 717 297;
- время построения: 7.93 секунды.

В готовой выдаче top-10 дополнение популярностью потребовалось двум Warm-пользователям.

|---|---:|---:|
| Все | 163.05 | 298 |
| Warm | 196.36 | 298 |

### Вклад ALS

Разница Candidate Recall между полным объединением и набором без ALS:

- все пользователи: 0.040237;
- Warm: 0.061493;
- Cold: 0.000000.

Для Warm добавление ALS увеличило полноту примерно на 6.15 процентного пункта.

ALS полезна как дополнительный источник кандидатов, несмотря на более низкое качество её самостоятельного top-10.

Объединённый набор больше отдельных списков. Это сравнение не использует одинаковый общий бюджет кандидатов.

Candidate Recall характеризует наличие будущих просмотров в наборе, но не гарантирует, что ранжировщик разместит их в первых десяти позициях.

## Ограничения текущей версии

Проект представляет собой offline-прототип. Production-инфраструктура пока не реализована.

Параметры задаются в коде, результаты записываются вручную. MLflow не подключён.

Модели не учитывают возрастные ограничения, доступность контента и метаданные пользователей и объектов при выдаче. Названия объектов используются для демонстрации.

Отсутствие просмотра не доказывает отсутствие интереса. Оценка основана на наблюдавшихся взаимодействиях и не устраняет смещение исторических показов.

Результаты получены на одной validation-неделе. Статистическая неопределённость и устойчивость на других временных окнах пока не оценены. Test остаётся нетронутым.

Рост покрытия и Candidate Recall сам по себе не доказывает улучшение итоговой выдачи. Улучшение offline-метрик не гарантирует роста продуктовых показателей — для этого потребуется A/B-тест.
